## 二、越权发布漏洞（RLS 缺陷，高危）

### 病状
迁移 `20260914181200_phase_a_core_tables` 中：

```sql
create policy notices_insert on public.notices
  for insert to authenticated with check (publisher_id = auth.uid() or app.is_admin());
```

因 `publisher_id` 默认 `auth.uid()`，**任何登录用户（含学生）都能插入通知**（把自己 uid 填进 publisher_id 即通过）。前端隐藏了发布按钮，但 RLS 才是真闸门。

### 实测确认
以学生 `20230301` 会话执行 `db.from('notices').insert({...})` → 返回 **201（成功）**。

### 修复
新增迁移 `20260914190000_fix_notice_publish_policy`：
- 新增 `app.is_super_admin()`（`SECURITY DEFINER`）。
- `notices_insert` → `with check (app.is_admin())`（仅 admin/superAdmin 可发布）。
- `notices_update` / `notices_delete` → `publisher_id = auth.uid() or app.is_super_admin()`（本人或超管）。

### 验证
- 学生再插入 → **403** `DATABASE_42501: new row violates row-level security policy for table "notices"` ✅
- 学生读通知 → 正常（1 条）✅
- 老师发布 → 仍成功 ✅

## 三、`must_change_password` 无法清除（改密后每次都强制改密）

### 病状
改密后再登录仍进改密页；查库发现 `must_change_password` 始终为 `true`。

### 根因
`docs/src/store.js` 的 `find/update/remove` 一律用 `.eq("id", id)` 定位行，但 **`users` 表主键是 `uid`，没有 `id` 列** → 更新报错，又被 `auth.js` 的 `.catch(function(){})` 静默吞掉。

### 修复
`store.js`：`COLLS` 增加 `idCol`（users→`uid`，其余→`id`），新增 `idColOf(coll)`，`find/update/remove` 统一改用该列；`add()` 对 users 不再自动生成 `id`。

### 验证
老师改密后查库 `must_change_password=false`；退出再登录**直接进应用**（不再强制改密）✅
